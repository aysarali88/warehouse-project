# Row-Level Security Convention

## Why RLS is mandatory

Supabase exposes the `public` schema through its Data API by default. Even though this application authorizes access through FastAPI server-side sessions, enabling Row-Level Security on every application-owned `public` table is required as defense in depth and prevents future Security Advisor warnings.

## Creating new public tables safely

Every migration that creates a new application table in `public` must enable RLS in the same migration:

```sql
CREATE TABLE public.example_table (
  id bigint generated by default as identity primary key
);

ALTER TABLE public.example_table ENABLE ROW LEVEL SECURITY;
```

The SQLAlchemy models also register an `after_create` hook that enables RLS automatically when SQLAlchemy creates a new PostgreSQL table. Migrations should still include the explicit SQL above so the database history is clear.

## Policies

Do not create permissive policies automatically. RLS should be enabled with no public policies by default. If direct Supabase `anon` or `authenticated` client access is introduced later, add narrowly scoped policies that match the real authorization model.

## Exceptions

An application table may keep RLS disabled only with an explicit documented exception in `docs/rls_exceptions.json`. Each exception must include a reason. Empty reasons or non-application table names fail validation.

## Verification

Run:

```powershell
python scripts/validate_public_rls.py
```

The validation fails if any non-exempt application-owned table in `public` has RLS disabled.

To print a table-by-table audit:

```powershell
python scripts/validate_public_rls.py --audit
```

To inspect all public tables directly in Supabase SQL editor:

```sql
SELECT tablename
FROM pg_tables
WHERE schemaname = 'public'
  AND rowsecurity = false
ORDER BY tablename;
```
